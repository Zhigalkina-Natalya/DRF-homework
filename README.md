# Django LMS Project

Учебный проект по разработке **LMS (Learning Management System)** — платформы для онлайн-обучения, где пользователи могут размещать свои курсы и уроки.

Проект реализован с использованием **Django** и **Django REST Framework**, **PostgreSQL**, **Redis**, **Celery** и **Docker**. 
Backend реализован как **REST API**, возвращающий JSON-ответы.

---
# Запуск проекта через Docker

## 1. Клонировать репозиторий

```
git clone https://github.com/Zhigalkina-Natalya/DRF-homework
```

## 2. Создать файл `.env`

Создайте файл `.env` в корне проекта.

Скопируйте файл `.env.sample` в `.env`:
```
cp .env.sample .env
```
Файл `.env.sample` содержит пример всех необходимых переменных окружения.

При необходимости измените значения (например, пароль базы данных или секретный ключ Django).

## 3. Запуск проекта

Запустить все сервисы одной командой:
```
docker compose up --build
```
Будут запущены следующие контейнеры:

- Django backend
- PostgreSQL
- Redis
- Celery Worker
- Celery Beat

# Django LMS Project — Часть 2

**Продолжение проекта LMS** — расширение функционала бэкенда.

### Основные изменения:
1. Поле `lessons_count`

Добавлено в сериализатор курса с помощью SerializerMethodField().
Теперь курс выводит количество уроков и их список одновременно.

2. Модель `Payment`

Создана в приложении users, содержит поля:
- user, paid_at, course, lesson, amount, payment_method.
- Способы оплаты: cash (наличные) и transfer (перевод).
- Данные можно загрузить через команду: `python manage.py create_sample_payments`

3. Фильтрация и сортировка платежей

Эндпоинт /users/payments/ поддерживает:
- фильтр по course, lesson, payment_method;
- сортировку по paid_at.

4. История платежей пользователя

В сериализаторе профиля добавлено поле payments.
Эндпоинт /users/<id>/ теперь возвращает список платежей конкретного пользователя.

### Примеры запросов (Postman)

`GET` `/materials/courses/1/`
→ возвращает курс с полями lessons_count и lessons.

`GET` `/users/payments/?payment_method=transfer`
→ фильтрация по способу оплаты.

`GET` `/users/1/`
→ профиль пользователя с историей платежей.

# Django LMS Project — Часть 3

**Продолжение проекта LMS** 

**Цель** — разграничение прав доступа и добавление проверки владельца объектов. 
По дополнительному заданию: ограничить доступ к профилю пользователя и разделить публичный/приватный просмотр.


### Основные изменения:

1. JWT-авторизация и регистрация пользователей

- Подключён `SimpleJWT` для аутентификации.

- Добавлен эндпоинт `/users/register/` для регистрации новых пользователей.

- Эндпоинты `/users/login/` и `/users/register/` доступны без авторизации, остальные — только авторизованным пользователям.

2. Роли и права доступа

- Создана группа **«Модераторы».**

- Модераторы могут **просматривать** и **редактировать** любые курсы и уроки,
но **не могут создавать или удалять** их.

- Для этого добавлен permission `IsModerator` и логика проверки во ViewSet’ах.

3. Привязка владельца и ограничение доступа

- В модели `Course` и `Lesson` добавлено поле `owner`.

- Обычные пользователи могут **просматривать** и **редактировать только свои объекты**.

- Реализованы permissions `IsOwner` и автоматическая привязка владельца при создании через `perform_create()`.

4. По дополнительному заданию: 
 - **Permission IsSelfOrReadOnly**
   1. Разрешает редактирование **только своего профиля**, но просмотр — любого авторизованного пользователя.

 - **Разделение сериализаторов**
   1. `UserSerializer` — детализированный профиль (с платежами).
   2. `PublicUserSerializer` — публичная версия без конфиденциальных данных.

 - **Динамический выбор сериализатора**
   1. Во `views` реализована логика:
      - если пользователь запрашивает **свой профиль** -> показывается полный;
      - если **чужой профиль** → ограниченный.

# Django LMS Project — Часть 5

**Продолжение проекта LMS** 

**Цель** — подключение платёжной системы `Stripe`, реализация создания и обработки платежей за курсы (и уроки), а также проверка статуса оплаты через API.


### Основные изменения:

1. **Интеграция со Stripe API**

- Подключена библиотека stripe.

- Добавлены ключи в .env: `STRIPE_SECRET_KEY` (используется для всех запросов к Stripe).

- Реализованы сервисные функции (users/services.py):

  - `create_stripe_product()` — создаёт продукт в Stripe;

  - `create_stripe_price()` — создаёт цену (в копейках);

  - `create_checkout_session()` — создаёт сессию оплаты и возвращает URL для Checkout;

  - `retrieve_session()` — получает информацию о сессии для проверки статуса.

2. **Модель платежей и связь с курсами**

- Расширена модель `Payment`:

  - добавлены поля `stripe_session_id`, `checkout_url`, `payment_status`;

- В модель `Course` и `Lesson` добавлены поля:

  - `stripe_product_id`;

  - `stripe_price_id`;
  
    (Эти значения позволяют избегать повторного создания продукта в Stripe при каждой оплате.)

3. **Создание сессии оплаты**

- Добавлен эндпоинт `POST /users/create-stripe-session/` для создания сессии оплаты.

- При запросе выполняются действия:

  1. Проверяется наличие продукта и цены в `Stripe` (если их нет — создаются и сохраняются в модели Course).

  2. Формируются `success_url` и `cancel_url` на сервере с использованием `request.build_absolute_uri()`.

  3. Создаётся `Stripe` `Checkout` `Session` и возвращается ссылка на оплату.

  4. Информация о платеже сохраняется в БД (Payment).

Пример ответа:
```
{
  "message": "Сессия оплаты создана для курса: Создание веб-приложений на Django",
  "checkout_url": "https://checkout.stripe.com/pay/cs_test_abc...",
  "stripe_session_id": "cs_test_abc..."
}
```
4. **Проверка статуса оплаты**

Добавлен новый эндпоинт `GET /users/check-payment/<stripe_session_id>/`,
который обращается к Stripe API и возвращает текущий payment_status,
а также обновляет его в модели Payment.

Возможные статусы: `open`, `unpaid`, `complete`.

5. **Визуальные страницы оплаты**

- Добавлены Bootstrap-шаблоны:

  - `/users/success/` — страница успешной оплаты;

  - `/users/cancel/` — страница отменённой оплаты.

Обе страницы отображают понятные сообщения и ссылку для возврата на главную.

### Пример потока оплаты:

1. Авторизованный пользователь создаёт сессию: `POST /users/create-stripe-session/`

2. Переходит по ссылке из ответа (`checkout_url`).

3. Оплачивает тестовой картой `4242 4242 4242 4242`.

4. После оплаты попадает на `/users/success/`.

5. Проверяет статус через: `GET /users/check-payment/<stripe_session_id>/`

# Django LMS Project — Часть 6

**Продолжение проекта LMS** 

**Цель** — добавить асинхронные задачи и автоматические фоновые процессы с использованием `Celery`, `Redis` и `celery-beat`.


### Основные изменения:
1. **Настройка Celery**

Проект настроен для работы с `Celery` — системой фоновых задач.

Добавлены файлы конфигурации:

- `config/celery.py` — основной файл настройки Celery

- `config/__init__.py` — подключение Celery при запуске Django

Celery использует Redis в качестве брокера сообщений и backend результатов.

Настройки вынесены в **переменные окружения**:
```
CELERY_BROKER_URL
CELERY_RESULT_BACKEND
```
В `settings.py` добавлены настройки:

- `CELERY_TIMEZONE`

- `CELERY_TASK_TRACK_STARTED`

- `CELERY_TASK_TIME_LIMIT`

2. Подключение celery-beat

Для выполнения **периодических задач** подключено приложение: `django_celery_beat`

В INSTALLED_APPS: `django_celery_beat`

Используется планировщик: `CELERY_BEAT_SCHEDULER = "django_celery_beat.schedulers:DatabaseScheduler"`

Периодические задачи описаны в `CELERY_BEAT_SCHEDULE`.

3. Асинхронная рассылка при обновлении курса

Добавлена Celery-задача: 
`materials/tasks.py`
`send_course_update_email(course_id)`

Задача:

- получает курс

- находит всех подписчиков (Subscription)

- отправляет email-уведомление

Письмо отправляется **асинхронно**, чтобы не блокировать основной поток API.

Задача вызывается из контроллера при обновлении курса.

4. **Ограничение частоты уведомлений**

Добавлена защита от слишком частых уведомлений.

В модели Course используется поле: `last_notification_at`

Логика:

- если курс обновлялся **менее 4 часов назад**

- уведомления **не отправляются повторно**

Это предотвращает спам-рассылку при частых обновлениях курса.

5. **Периодическая блокировка неактивных пользователей**

Добавлена фоновая задача:

`users/tasks.py`
`deactivate_inactive_users`

Задача:

- проверяет поле `last_login`

- если пользователь **не заходил более 30 дней**

- его аккаунт автоматически блокируется:

`is_active = False`

Задача запускается **ежедневно** через `celery-beat`.

6. **Логирование фоновых задач**

Для задач `Celery` настроено логирование.

Логи сохраняются в файл: `logs/tasks.log`

Отслеживаются:

- отправка писем

- ошибки отправки

- блокировка пользователей

- выполнение задач

### Как запустить Celery
1. Запустить Redis `redis-server` 
2. Запустить Celery Worker `celery -A config worker -l info`
3. Запустить Celery Beat `celery -A config beat -l info`
4. Запустить Django `python manage.py runserver`
